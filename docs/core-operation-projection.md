# Recorded execution exports

`RuntimeOwner::project_operation` reads one consistent snapshot of a managed operation and returns an authority-neutral `Operation`. Its `OperationState::Execution` contains the recorded lifecycle, revision, current attempt, original or compensation phase, and selected evidence. There is no second summary state to disagree with it and no API that imports this record as execution authority.

Transport acceptance remains `accepted`, with no verified outcome. An uncertain transport result remains `needs_reconciliation`; authenticated inconclusive evidence stays distinct from an absent observation and from proven non-commit. Verified evidence retains read captures, local before/after revisions, or external receipt hashes in their own outcome variants. Content hashes are not converted into provider receipt IDs. `Receipt` retains its existing meaning and representation.

The projection preserves an unstarted pending attempt, including after local cancellation. Compensation retains a separate operation, attempt and evidence. A compensated original keeps its own evidence and refers to the verified compensation. The reconciliation timestamp includes the later compensation evidence. Both sides validate the original account, privacy scope, attempt and recorded receipt reference.

The reader validates stored evidence hashes, canonical payloads, identity and attempt bindings, effect and source domains, outcome columns and observation times. It selects one deterministic decisive observation, or the latest inconclusive observation when no decisive outcome exists. It rejects conflicting final outcomes. Evidence selection and compensation joins return bounded records and do not recursively traverse history. This is an inspection of evidence authenticated when recorded; it does not repeat cryptographic authentication with a current trust key or establish provider settlement independently.

The runtime has no recorded idempotency key, so execution exports omit it. Constructors and imports reject an execution record that supplies one. Legacy operation documents still require and preserve their recorded key. `Operation::new` now returns a validation result; `Operation::from_execution` creates the checked observation form. Unknown fields, unknown labels, impossible state/evidence combinations and inconsistent reconciliation times fail decoding.

This is a pre-freeze schema-1.0 extension. Existing operation and receipt fixtures keep their meanings; older strict readers reject the new execution variant. Unmanaged or legacy unbound durable operations cannot be exported as a managed execution observation. A legacy combined `compensating` state is refused because it lacks the separate managed lineage required by this projection. The read API does not backfill missing facts, change durable state or create receipts.

`fixtures/core/execution-records-v1.json` extends the existing operation conformance check with accepted, inconclusive, verified and compensated records. The same records pass schema-1.0 validators, canonical import and control-envelope decoding; malformed nested fields and invented keys are rejected. The original full/minimal legacy fixture remains in the thirteen-family catalogue.

This increment does not by itself accept CORE-01.T03. Exact-source verification, whole-schema compatibility sign-off and independent task acceptance remain required. Provider-target execution and provider transformations are downstream implementation boundaries; this record layer preserves their meaning and refuses unsupported execution.
